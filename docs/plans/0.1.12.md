# v0.1.12: parallel work you can trust

v0.1.12 makes the TUI and the CLI the best place to run several pieces of
software and research work at once. The goal is that a user can hand QQ
three changes and a research question in one sitting, keep typing while
they run, and land each result knowing exactly what it changed and that
it was checked. Nothing in front of the user waits on something the agent
could do in the background.

It builds on the v0.1.11 TUI ([plan](0.1.11.md)): the dock, the switcher,
agent lanes and turn receipts. Remote daemons, saved servers, sessions
from other workspaces, pairing (ADR-0015), desktop and mobile are out of
scope.

Issues carry assignments and verification. Remove a section when it ships.

## The idea

Every competitor in `.source/` either runs writing agents in one shared
checkout (fx, Codex) or isolates them without bringing the work back (t3code
gives each thread a worktree but never compares or merges; opencode keeps
worktree tools behind Code Mode; pi has no built-in sub-agents). None of
them ties the conversation to the state of the files: pi's fork restores
the chat but not the code, and Codex reviews a diff with no rollback point.

QQ's answer is one model that the sections below implement:

- **Every turn has a checkpoint.** A turn's file changes are a Git tree you
  can diff, rewind to, or fork from.
- **Every writing agent works in its own worktree** and hands back a
  **change**: a diff against a known base, the checks it ran, what it cost.
- **A change is landed, discarded or compared** by the parent agent or the
  user, with overlaps named before landing.
- **Tools run as wide as their declared paths allow**, and checks run after
  edits without making the agent wait.
- **One view shows every piece of running work** across sessions, agents
  and background commands.

## Rules for every section

1. **The user's checkout is changed only by the user, a root session, or a
   landed change.** A writing child never edits it directly.
2. **Nothing waits that could run beside it.** A check, a checkpoint, a
   compaction summary or a fetch that the next step does not need runs in
   the background and reports when it lands.
3. **Every background thing has an owner and a lifetime** that the user can
   see and stop.
4. **Show cost where the work is.** A change, a lane and a receipt carry
   their own spend and cache hits.
5. **Persist before publish**, bounded queues, no lock across `.await`, as
   everywhere else. A protocol change regenerates
   `crates/qq-protocol/tests/fixtures/` and bumps `PROTOCOL_VERSION`
   (`crates/qq-protocol/src/lib.rs:82`, 42 today). Each PR says whether it
   needs one.

## Evidence

Read from `main` at `4ff19214`.

**Delegation.**
- A run may have 3 children at once, 8 in total, depth 3
  (`crates/qq-core/src/sessions.rs:348-352`).
- Write children are serialized by a per-run `Semaphore::new(1)`
  (`crates/qq-core/src/sessions/subagents.rs:348`, acquired at `:726-733`)
  and always block the parent (`docs/design/architecture.md:1432-1435`).
- Every child runs in the parent's checkout: the load request takes
  `claimed.workspace` (`crates/qq-core/src/sessions/execution.rs:705-711`),
  and the child row gets the parent's `workspace_id`. Safety comes from
  per-file compare-and-swap (`docs/design/tools.md:1081-1112`). Worktree
  isolation is listed as deferred (`tools.md:1612-1613`).
- A child's result is text only: `ChildAnswer { content, is_error }`
  (`crates/qq-core/src/sessions/deliveries.rs:12-15`). No diff, no file
  list, no checks.
- The parent can wait on or cancel a child, but cannot message one. Steering
  exists per run (`crates/qq-core/src/sessions/runtime.rs:662-674`) and a
  child is an ordinary run, so the hook is there.
- Each child re-reads config, `AGENTS.md` and skills from disk when it loads
  (`crates/qq-host/src/runtime.rs:2067-2123`, `crates/qq-core/src/plan.rs:654`).

**Snapshots.**
- One snapshot per run, before its first file-changing call
  (`execution.rs:2564-2576`), stored as `refs/qq/snapshots/<run>`
  (`crates/qq-core/src/undo.rs:10`), 50 kept (`undo.rs:12`), Git 2.32+.
- Nothing is per turn. There is no session fork; `/rollback` only drops the
  last compaction and touches no files
  (`crates/qq-core/src/sessions/commands.rs:1847-1880`).

**Tool scheduling.**
- Only calls classified `ReadOnly` overlap, at most 4
  (`crates/qq-core/src/lib.rs:138`,
  `crates/qq-core/src/runtime/run_loop.rs:2978-2987`). The first non-read
  call makes every later call in the turn serial
  (`run_loop.rs:3031-3033`).
- Edits already take a per-canonical-path `apply_lock`
  (`crates/qq-core/src/workspace/access.rs:390-400`).

**Background work.**
- At most 16 yielded commands per run (`crates/qq-core/src/tools/commands.rs:15`),
  all cancelled when the run ends (`commands.rs:160-169`). Clients cannot
  see them: the table is in memory and the protocol has no type for it.
- A run waiting on an approval or a question keeps its admission permit
  (`crates/qq-core/src/sessions/approvals.rs:129-171`; the permit drops only
  at `crates/qq-core/src/sessions/scheduler.rs:172`). `max_active_runs` is a
  hard-coded 8 (`runtime.rs:311`).

**Speed.**
- Every shell call is a fresh `/bin/sh -c` (`crates/qq-core/src/tools/shell.rs:787-791`),
  so commands that need the user's login environment re-source it or go
  without it.
- Each session, children included, uses its own id as the prompt-cache key
  (`execution.rs:449`), so a child never reuses its parent's cached prefix.
  Cache reads are recorded (`TokenUsage.cache_read_input_tokens`) but the
  TUI folds them into one token total and `qq run` text output never shows
  them.
- In-run compaction blocks the run while it summarizes
  (`run_loop.rs:1164-1189`). The summary points to `search_history`, not to
  the stored turns (`sessions.rs:366-378`).
- No check runs after an edit; there is no hook or config key for one.

**Research.**
- `fetch` has no cache (deferred in `docs/design/tools.md:1322`) and the
  session keeps no record of sources.

## W. Writing agents in their own worktree

A write child gets a Git worktree of its own and works there. This removes
the one-writer rule, so up to the concurrency cap of writing children run
at once.

**Shape.**
- A session gains an `execution_root`: `Checkout` (today) or
  `Worktree { root, base: Oid, branch }`. It is recorded on the session row
  when the child is admitted, before the child's first turn.
- The worktree lives under the QQ data dir, keyed by session id, on a branch
  `qq/<parent-short>/<child-short>`. `base` is the parent's current
  checkpoint (section K), so uncommitted work in the parent is in the
  child's tree.
- File tools and shell resolve against `execution_root` instead of
  `claimed.workspace`. `Workspace::open` and `process_context` already take
  a root; the change is which root the loader passes
  (`execution.rs:705-713`) and the `workspace_path` check after load.
- **Config, trust, instructions and skills are pinned from the parent's plan
  at spawn**, not re-read from the worktree. A child that edits `.qq/` or
  `AGENTS.md` in its branch cannot widen its own authority or rewrite its
  own instructions.
- Ignored files the build needs are not in a fresh worktree. A workspace
  may list globs in `.qq/worktree-include`; they are copied (reflinked where
  the filesystem supports it) at creation. `target/` is not copied by
  default; `CARGO_TARGET_DIR` is set to a per-worktree directory under the
  data dir so the child's build doesn't fight the parent's lock. The PR
  measures the cold-build cost and says whether sharing a target dir is
  worth it.
- Outside a Git repository, or when worktree creation fails, a write child
  falls back to today's behavior and the spawn result says so.

**Lifetime.** A worktree lives until its change (section H) is landed or
discarded, or the session is deleted. Retention removes worktrees of
settled sessions after the store's retention window, keeping the branch's
tree as a ref so the change can still be shown.

**Accepted when:**
- Two write children edit the same file at once in different worktrees and
  neither sees the other's edit; the user's checkout is unchanged until a
  land.
- A child that edits `.qq/config.ron` in its worktree runs with the parent's
  config (test against the loaded plan).
- `delegation.write_children` still gates write children; the write
  semaphore is deleted.
- `docs/design/tools.md` (shared-checkout section and Intentionally
  Deferred) and `architecture.md` (write children block) are updated.

## H. A writing agent hands back a change

A write child's result becomes a **change**: a durable record the parent
and the user act on.

**Shape.**
- `Change { id, session, base: Oid, head: Oid, files: [path, +, −],
  checks: [CheckResult], spend, state }` where state is `Open`, `Landed`,
  `Discarded` or `Conflicted`. It is stored with the child's session and
  published as a session event.
- The child's runtime notice to the parent carries the change: its id, the
  diffstat, the checks that ran and their outcome, then the child's answer.
  The parent no longer has to ask "what did you change?".
- New tools for the parent, declared exactly when write children are:
  - `show_change(id, path?)` returns the diff, bounded like any tool result
    with a spill handle for the rest.
  - `land_change(id)` applies the change to the parent's execution root as
    a three-way merge from `base`. A clean merge lands; any conflict lands
    nothing and returns the conflicting paths.
  - `discard_change(id)`.
- **Overlap is named before landing.** When two open changes from one
  parent touch the same path, both notices say so, and `land_change` on the
  second reports the overlap even if the merge is clean.
- **Compare.** Spawning the same task N times (for example with different
  models) gives N changes. `compare_changes(ids)` returns their diffstats,
  checks and spend side by side. Picking one discards the others only when
  asked.
- The user sees changes in the TUI: a change row under the spawn lane
  (`● Changed 3 files +40 −6  ✓ checks  $0.18`) that opens the diff in the
  dock, with `l` land, `x` discard, `d` diff. `/changes` (today a file
  list, `docs/guide/tui.md:257-261`) becomes the list of open changes.
- CLI: `qq changes [--session ID]` lists them; `qq land ID` and
  `qq discard ID` act on them. `qq run --format jsonl` emits
  `change_opened` and `change_landed` records.
- Landing records a snapshot first, so `qq undo` reverses a land.

**Accepted when:**
- Tests cover a clean land, a conflicting land that changes nothing, an
  overlap notice on a clean merge, discard, and land after the parent
  edited a different region of the same file.
- A crash between merge and record leaves either the old tree or the landed
  tree, never a half-applied one (the merge is written to the index and
  checked out in one step, after the change row is marked `Landing`).
- A three-child fan-out from `qq run` produces three change records in
  JSONL with matching diffstats.

## K. A checkpoint for every turn, and fork that restores files

**Checkpoints.**
- At each turn boundary of a run that changed files, QQ writes a tree of
  the execution root through a temporary `GIT_INDEX_FILE` and stores it as
  `refs/qq/turns/<session>/<turn>`, with the same untracked-file limits as
  run snapshots (`undo.rs:14`). It runs off the turn's critical path: the
  next model request starts while the checkpoint is written, and the
  following tool call that may change files waits for it.
- Unchanged trees write no ref. Run snapshots (`refs/qq/snapshots/`) stay;
  the first turn checkpoint of a run is its snapshot, so the two share code.
- Retention is per session: the last 200 turn refs, plus every turn a
  change or a fork points to.

**What they give.**
- **Turn diff.** The v0.1.11 turn receipt opens to that turn's diff,
  computed checkpoint to checkpoint, so edits pulled in by `git pull`
  between turns are not attributed to the agent.
- **Rewind.** `/rewind` opens a turn picker in the dock; choosing a turn
  restores the files to that checkpoint (recording a before-snapshot, as
  `qq undo` does) and marks later turns as rewound. The transcript keeps
  them, folded.
- **Fork.** `/fork` on a prompt (block cursor `f`, or `/fork` with a turn
  picker) creates a new session whose history is everything before that
  prompt, whose execution root is a worktree at that turn's checkpoint, and
  whose composer holds the prompt for editing. The original session is not
  touched. CLI: `qq fork SESSION [--turn N]`.

**Accepted when:**
- A test edits a file over three turns and shows each turn's diff exactly.
- Rewind to turn 1 restores the file, and `qq undo` brings turn 3 back.
- Fork at turn 2 gives a session with the turn-1 history and the turn-1
  files, while the source session's files are unchanged.
- A turn boundary with a checkpoint pending adds no model-request latency
  (measured with the loopback fake; the number goes in the PR).

## P. Run tool calls as wide as their paths allow

Replace "only leading reads overlap" with scheduling by what each call
touches.

**Shape.**
- Each call gets an `Access` from its arguments before it runs:
  `Read(paths)`, `Write(paths)`, `Workspace` (anything else: shell that
  isn't read-only, external tools without `read_only`, goal and selection
  tools) or `None` (network, waits on children, `command_status`).
  `read_file`, `search`, `tree` read their path; `edit_file` and
  `write_file` write theirs; a read-only shell command reads the workspace.
- Calls run in model order through a conflict check: a call starts when no
  running call writes a path it touches, and a `Workspace` call waits for
  everything before it and blocks everything after it. Results are still
  observed and recorded in call order, as today (`run_loop.rs:3140-3144`).
- The cap of 4 becomes a limit on concurrent calls of 8, still bounded.
- This deletes the `serial_suffix` rule (`run_loop.rs:3031-3033`) and the
  separate read-batch path; one scheduler handles every call.

**Accepted when:**
- A turn of `read a, edit b, read c, edit d` runs all four at once, and
  `edit a, read a` runs in order (tests on start order with a fake clock).
- Two edits to one file in one turn apply in model order.
- The tool-dispatch bench reports a turn of six mixed calls against
  today, interleaved and pinned to one core.

## V. Checks after edits, without waiting

**Shape.**
- A `checks` config section maps globs to commands:

  ```ron
  checks: [
      (paths: ["**/*.rs"], run: "cargo check --message-format short", timeout_seconds: 120),
      (paths: ["**/*.ts", "**/*.tsx"], run: "tsc --noEmit"),
  ],
  ```

  Project checks are project config and need trust like any other project
  command.
- After a turn's last edit to a matching file, the check starts in the
  execution root as a background command owned by the turn. A newer edit
  cancels and restarts it (debounced to the end of the turn's tool calls).
- When it finishes, failures arrive at the next turn boundary as a runtime
  notice: the command, the exit status and the first 40 lines of output
  with a spill handle. A pass sends nothing to the model and shows `✓` on
  the turn receipt.
- A run does not settle while a check it started is running; its final
  answer comes after the result, so "done" means checked.
- A change (section H) carries the last check result of its child.

**Accepted when:**
- A test edits a Rust file to a compile error and the next turn's context
  carries the error; fixing it gives no notice and a `✓`.
- Three rapid edits run the check once.
- A failing check never blocks the edit call itself (timing test with the
  loopback fake).

## J. One view of all running work

**Shape.**
- A `Work` item is anything running or waiting: a run, a child, a yielded
  command, a check, a queued prompt, an open change. Each carries its owner
  session, state, started time, last activity and spend.
- **Command lifetimes.** `shell` and `exec` take `lifetime: turn | session`
  (default `turn`, today's behavior). A `session` command (dev server,
  watcher) survives the run's end and is owned by the session until it
  exits, is stopped, or the session is deleted. The per-run cap of 16
  stays; `session` commands have their own per-session cap of 8.
- Yielded commands become visible to clients: a protocol type for a
  command's id, argv summary, state, lifetime and output size, and its live
  output through the existing tool-output stream.
- **TUI.** `Ctrl-W` opens the work panel in the dock: every item, grouped by
  session, newest activity first, with `Enter` to focus its session or open
  its output, `k` to stop it and `l`/`x` on changes. The rule's right edge
  counts running work as well as needs.
- **CLI.** `qq ps` lists running work across the workspace's sessions
  (`--json` for scripts); `qq stop ID` stops one item.

**Accepted when:**
- A dev server started with `lifetime: session` is still answering after
  the run ends, shows in `Ctrl-W` and `qq ps`, and stops with `k`.
- A test asserts every work kind appears with its owner, and that a hidden
  session's command output does not wake a frame.

## M. Talk to a running agent

- New parent tool `message_agent(id, text)`, declared with `spawn_agent`.
  The text is delivered as steering to the child's run at its next turn
  boundary, without cancelling the tool it is running. The child sees it
  as a message from its parent, not as a user instruction.
- In the TUI, focusing an agent (lane `Enter`) and typing steers it, as for
  any session. The child's transcript marks who sent each message.
- The answer to `message_agent` says whether the text was queued for a live
  run or the child had already settled.

**Accepted when:** a test steers a child mid-turn and shows the child's next
request carries the message while its running tool completed normally.

## S. Shell startup once, not per command

- On the first shell call of a runtime, QQ runs the user's login shell once
  (`$SHELL -lc 'env -0'`, bounded to 5 s) and captures the environment.
  Later commands start `/bin/sh -c` with that environment merged under the
  process context QQ already sets.
- The capture is refreshed when a startup file it read changes (mtime
  check, no watcher) or on `/shell reload`.
- `shell.login_environment: false` turns it off. A capture that fails or
  times out is skipped with a one-time notice; commands still run.

**Accepted when:** a test with a fake login shell that sets a variable and
sleeps shows the variable in every later command and the sleep paid once;
the PR reports per-command spawn latency before and after.

## C. Make prompt caching visible and shared

- A read child created by `spawn_agent` without a model override uses its
  parent's cache key, since its request prefix (system prompt and tools)
  matches. Children with a different model or tool set keep their own.
- Record, per model turn, why the cached prefix was not reused when the
  provider reports fewer cache reads than the previous turn's prefix: model
  changed, tools changed, system changed, compaction, or expired.
- Show cache reads: the turn receipt shows `cache 92%`; `qq run` text
  output prints input, cached and output tokens on its final line; the work
  panel shows a child's hit rate.
- Custom and LiteLLM endpoints that speak the OpenAI Responses API get the
  session cache key as well (today they send none,
  `docs/design/providers.md:101-118`).

**Accepted when:** a test with the loopback fake asserts a read child's
first request carries the parent's key, and a changed tool set records
`tools changed`.

## Z. Compaction that doesn't stop the run

- When the estimated context passes 80% of the compaction threshold, start
  the summary in the background from the transcript up to the current
  turn. When the threshold is reached, swap in the precomputed summary and
  summarize only the turns after its cutoff. If the precompute is not done,
  wait for it rather than starting a second one.
- The summary request and the swap stay exactly as ADR-0039 defines them;
  only the start time moves. Its usage stays on its own run row.
- The summary preamble names the stored turns: each summarized turn is
  listed with a handle that `read_tool_result` opens, so the agent can get
  any tool result back verbatim, not only by `search_history`.

**Accepted when:** a long scripted run with the loopback fake shows no
`Compacting` activity longer than one fake turn at the threshold, and the
compacted context names handles that open the original results.

## F. Research that fans out and keeps its sources

- `fetch` gets a per-session cache keyed by URL, honoring `ETag` and
  `Last-Modified` with conditional requests, bounded to 64 MiB per session.
  A cache hit says so.
- Every fetched page is stored as a **source** on the session: URL, final
  URL, title, fetched time, and a spill handle to the converted text.
  Sources from read children roll up to their parent.
- `/sources` in the TUI and `qq sources SESSION` list them. An answer that
  cites a URL from the session's sources gets that URL linked in the
  transcript (OSC 8).
- The research guidance in the system prompt says to fan out read children
  for independent questions and to cite sources by URL. No new tool.

**Accepted when:** a test fetches a page twice and the second request is
conditional; a parent's `/sources` lists pages its read children fetched.

## Q. Review against a checkpoint

- `/review` becomes built in (today it resolves only a workspace skill,
  `crates/qq-core/src/lib.rs:3066-3079`). It reviews a target, by default
  the focused session's changes since its last user prompt; also a turn, a
  change, or `--base REF`.
- The review runs as a read child with a clean context: it gets the diff,
  the user's request and the session's instructions, not the
  conversation. It may use its own model (`review.model` in config).
- Findings come back as structured items (path, line, severity, text). The
  TUI shows them on the diff in the dock; `Enter` on a finding sends it to
  the session as a steering message. Each finding names the checkpoint it
  was made against, so `/rewind` to it is one key.
- `qq review [--session ID] [--base REF] [--format jsonl]` runs it from the
  CLI with an exit code that reports whether any blocking finding exists.

**Accepted when:** a test reviews a fake change and gets findings anchored to
lines in that change; the CLI exits non-zero on a blocking finding.

## R. Room for the parallel work

Without these, sections W and J hit the admission limit before the user
does.

- **Waiting runs give up their slot.** A run held on an approval or an
  `ask_user` question releases its admission permit and takes one back,
  ahead of queued runs, when answered.
- `max_active_runs` becomes a config key, defaulting from available
  parallelism (minimum 8), and is reported by `qq doctor`.
- File-tool blocking permits scale with available parallelism instead of
  the fixed 8 and 16.

**Accepted when:** with `max_active_runs: 2`, two runs held on approvals let
a third run start, and answering one resumes it ahead of a queued fourth.

## Not doing

- **A sandbox for scripts the model writes** (pi's and opencode's Code
  Mode). Section P gets most of the parallel-call benefit; the sandbox
  brings its own class of bugs.
- **A model that reviews each risky action** (fx). QQ removed it in v0.1.10.
- **An in-process extension API.** MCP and skills stay the extension points.
- **Share links, a plan checklist tool, idle cache warming.** Not worth the
  surface for one user's daily work.
- **Merging changes automatically.** A change lands only when the parent or
  the user lands it.

## Order

1. **K** first: checkpoints are the base that W, H, Q and fork use.
2. **R** and **S** in parallel with K; both are small and independent.
3. **W**, then **H**. H depends on W's execution root and K's checkpoints.
4. **P** and **V** after W, since both resolve paths against the execution
   root.
5. **J** after H (changes are work items) and V (checks are).
6. **M**, **C**, **Z**, **F**, **Q** whenever there is room; Q needs K and H.

Each PR shows its regression test failing before the change, drives the
real loop or TUI, updates `docs/design/` and `docs/guide/` where they become
wrong, reports any protocol bump, and runs `cargo xtask check` once.

## Release check

On the final build, in a scratch repository, with the loopback fake and
then once with a real model within a stated spend cap:

1. Ask for three independent changes in one prompt. Record that three
   write children ran at once, the user's checkout was unchanged until
   landing, and each change carried a diff and a check result.
2. Make two of them touch one file. Record the overlap notice and the land
   result.
3. Rewind a session two turns, fork it from its first prompt, and confirm
   files match each checkpoint.
4. Start a dev server with `lifetime: session`, end the run, find it in
   `qq ps` and stop it from `Ctrl-W`.
5. Run a research question that fans out to three read children; record
   `/sources` and the cache hit rate on the receipt.
6. Run `/review` on a landed change and send one finding back.

Report each result as observed against v0.1.11 on the same host, including
failures.
