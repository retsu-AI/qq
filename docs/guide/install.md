# Install

QQ is a single static binary. Pick one route; every route ends with the same
`qq` on your `PATH`.

## Install script (Linux, macOS)

```sh
curl -fsSL https://retsu-ai.github.io/qq/install.sh | sh
```

The same script is in the repository as `install.sh`; the site serves the
copy from the latest `main`. The script detects your OS and CPU, downloads the matching archive from the
latest [GitHub release](https://github.com/retsu-AI/qq/releases), verifies it
against that release's `SHA256SUMS`, and installs `qq` into `~/.local/bin`.
It never uses `sudo`; if the directory is not on your `PATH`, it prints the
line to add. It supports Linux x86_64 and aarch64 (static musl, any
distribution) and macOS Intel and Apple silicon, and refuses anything else
with a pointer to the releases page.

Pin a version or change the directory with flags or environment variables:

```sh
curl -fsSL https://retsu-ai.github.io/qq/install.sh | sh -s -- --version 0.1.9 --dir /opt/qq/bin
QQ_VERSION=0.1.9 QQ_INSTALL_DIR="$HOME/bin" sh install.sh
```

`sh install.sh --help` lists the options. To upgrade, run it again.

The script retains each executable by its SHA-256 in
`~/.local/bin/.qq-versions/qq-<sha256>` (or `.qq-versions` inside your chosen
install directory). `qq` is a relative symlink selecting one payload. Updates
stage a complete, read-only executable on the same filesystem, publish it
without overwriting an existing payload, then atomically replace the selection
link. An existing regular executable is copied and checksum-verified into the
retained directory before replacing it; its bytes are preserved for rollback.
Payloads are not automatically pruned.

Rerun with `--version X.Y.Z` to roll back to a published release; matching
retained bytes are verified and reused. For a legacy executable without a
published release, locate its retained checksum and select it explicitly:

```sh
cd "$HOME/.local/bin"  # or your chosen install directory
payload_sha=REPLACE_WITH_FULL_RETAINED_CHECKSUM
ln -s ".qq-versions/qq-$payload_sha" .qq-rollback
mv -f .qq-rollback qq
```

Replace `REPLACE_WITH_FULL_RETAINED_CHECKSUM` with the full retained checksum. Do not select an old
binary against an incompatible migrated store: follow the backup/rollback
instructions below. Stop QQ clients and servers before updating and restart
them together. Retention does not fix macOS Keychain authorization or promise
that running processes can safely use a different version.

Foreign or dangling selection links, special nodes, multiply hardlinked
executables, and corrupt retained payloads are refused without replacing the
selection. Inspect and move conflicting files aside yourself; the installer
does not repair or delete them. If interrupted during publication, rerun the
installer: it either publishes again or verifies/reuses the complete payload.
Stale `.qq-install.*` directories from a killed installer are left untouched;
after confirming no installer is running, inspect and remove those staging
directories yourself. This is interruption recovery, not protection against
concurrent same-user filesystem changes or a guarantee of durability after
power loss (the shell installer does not fsync).

## Homebrew (macOS, Linux)

```sh
brew install retsu-ai/qq/qq
```

The formula in the `retsu-AI/homebrew-qq` tap is generated by the release
workflow from each release's `SHA256SUMS`, so it always points at the
archives above. Homebrew does not pin versions of tap formulae;
pin with `install.sh --version` instead.

## Nix

```sh
nix run github:retsu-AI/qq -- --version    # run without installing
nix profile install github:retsu-AI/qq     # install into your profile
```

The flake exposes `packages.qq` (also `packages.default`) built from source
with the pinned toolchain, and `apps.default` runs it. Pin a release with a
ref: `nix run github:retsu-AI/qq/v0.1.9`. `nix build .#qq` inside a clone
builds the same package; `nix develop` gives a shell with the exact
toolchain.

## cargo-binstall

```sh
cargo binstall --git https://github.com/retsu-AI/qq qq
```

[`cargo-binstall`](https://github.com/cargo-bins/cargo-binstall) reads the
`[package.metadata.binstall]` table in `Cargo.toml` and downloads the
release archive for your target instead of compiling. Pass
`--version 0.1.9` to pin. The `--git` form is required because the crate is
not published on crates.io; a plain `cargo binstall qq` would resolve a
different crate of the same name.

## From source

Requires the pinned stable Rust toolchain (`rust-toolchain.toml` selects it
automatically inside the repository):

```sh
cargo install --git https://github.com/retsu-AI/qq --locked qq            # latest main
cargo install --git https://github.com/retsu-AI/qq --tag v0.1.9 --locked qq
```

or from a clone: `cargo build --release` and install
`target/release/qq`. `cargo build --release --no-default-features` builds the
minimal profile without the Amazon Bedrock family and its AWS SDK dependency
closure; use it when you only need the HTTP providers.

## Windows

Download `qq-vX.Y.Z-x86_64-pc-windows-msvc.zip` and `SHA256SUMS` from the
[latest release](https://github.com/retsu-AI/qq/releases/latest), check the
hash with `Get-FileHash`, extract `qq.exe`, and put its folder on `Path`.
`cargo binstall --git https://github.com/retsu-AI/qq qq` also works on
Windows and does the download and check for you.

## Verifying downloads

Every release attaches one archive per target and a `SHA256SUMS` file
covering all of them:

| Target | Archive |
| --- | --- |
| Linux x86_64 (static musl) | `qq-vX.Y.Z-x86_64-unknown-linux-musl.tar.gz` |
| Linux aarch64 (static musl) | `qq-vX.Y.Z-aarch64-unknown-linux-musl.tar.gz` |
| macOS Apple silicon | `qq-vX.Y.Z-aarch64-apple-darwin.tar.gz` |
| macOS Intel | `qq-vX.Y.Z-x86_64-apple-darwin.tar.gz` |
| Windows x86_64 | `qq-vX.Y.Z-x86_64-pc-windows-msvc.zip` |

`install.sh`, Homebrew, and cargo-binstall verify the archive against these
sums before installing; a mismatch installs nothing. To verify by hand:

```sh
V=0.1.9 T=x86_64-unknown-linux-musl
curl -fsSLO "https://github.com/retsu-AI/qq/releases/download/v$V/qq-v$V-$T.tar.gz"
curl -fsSLO "https://github.com/retsu-AI/qq/releases/download/v$V/SHA256SUMS"
sha256sum --ignore-missing -c SHA256SUMS      # macOS: shasum -a 256 --ignore-missing -c SHA256SUMS
tar -xzf "qq-v$V-$T.tar.gz" && install -m 755 "qq-v$V-$T/qq" ~/.local/bin/qq
```

macOS may quarantine a binary downloaded by a browser. If `qq` is blocked,
run `xattr -d com.apple.quarantine qq` once; `curl`-based routes are not
affected.

## What the shell sandbox needs

Agents run `shell` and `exec` commands through a separate command worker
that confines them with the operating system's own isolation. QQ has no
unsandboxed fallback: when that isolation is unavailable, commands do not
run in any approval mode. Reading, searching, and editing files do not need
it, and `read_only` never runs commands.

### Linux

| Requirement | Needed by | Check |
| --- | --- | --- |
| Run as an ordinary user, not root or setuid | every mode | `id -u` is not `0` |
| Unprivileged user namespaces | `ask`, `auto`, `full` | the `unshare` command below succeeds |
| A root-owned util-linux `unshare` on `PATH`, in root-owned directories that only root can write, not a script | `ask`, `auto`, `full` | `ls -l "$(command -v unshare)"` shows `root root` and no group/other write bit |
| The `qq` binary not group- or world-writable | `ask`, `auto`, `full` | `ls -l "$(command -v qq)"` |
| Landlock ABI 6 (Linux 6.12 or newer, with `landlock` in the active LSM list) | `auto` | `uname -r`; `cat /sys/kernel/security/lsm` lists `landlock` |
| seccomp, on x86_64 or aarch64 | `auto` | `uname -m` |
| About 768 MiB free on the data directory's disk for task copies | `auto` | `df -h` on the `data:` path from `qq config paths` |

Check namespaces as the user that runs QQ:

```sh
unshare --user --map-current-user --pid --fork --kill-child=KILL --mount-proc -- true
```

If that prints `unshare failed: Operation not permitted`, the host blocks
unprivileged user namespaces. Fix this before using QQ there; see
[Troubleshooting](troubleshooting.md#the-first-shell-command-ends-the-run-session-runtime-is-unavailable).
Common causes:

- **Ubuntu 23.10 and later (including 24.04)** restrict them with AppArmor.
  Allow them with
  `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0`, and make
  that persistent in `/etc/sysctl.d/`, or add an AppArmor profile for
  `unshare` that permits `userns`.
- **Docker and other container runtimes** block `unshare` with their default
  seccomp and AppArmor profiles and often run as root. Run QQ as a non-root
  user, with a seccomp/AppArmor profile that allows user namespaces and
  mounting `proc`.
- **Hardened kernels** may set `kernel.unprivileged_userns_clone=0` or
  `user.max_user_namespaces=0`.

QQ does not need cgroups, systemd, or D-Bus for ordinary commands.

### macOS

Run as an ordinary user. Commands run under the built-in
`/usr/bin/sandbox-exec`. The `qq` binary must not be group- or
world-writable.

### Windows

No setup is needed. Auto uses a restricted token and job objects. This is
weaker than Linux and macOS: it also permits writes wherever Everyone or
your logon session can already write, and commands use the host network.
See [Permissions › Native Auto execution](permissions.md#native-auto-execution).

## Check the install

```sh
qq --version        # qq 0.1.9 (6809a21 2026-10-26)
qq version          # adds the protocol, capabilities, descriptor, and store schema versions
qq config paths     # where QQ will look for configuration and keep sessions
```

## Upgrade

Rerun the route you installed with (`install.sh`, `brew upgrade qq`,
`nix profile upgrade`, `cargo binstall --git … qq`). QQ uses 0ver: a patch
release can change compatibility contracts. Read the release's **Upgrading**
notes before upgrading. Locate the session store in the `data` directory
printed by `qq config paths`. For a safe backup, stop every QQ process
(`qq serve`, the TUI, and any `qq run`) and copy `sessions.sqlite3` together
with any adjacent `sessions.sqlite3-wal` and `sessions.sqlite3-shm` files.
If QQ must stay running, use SQLite's consistent `.backup` instead; do not
copy a live database or data directory non-atomically. Follow the absolute-path
backup and rollback procedure in the release's **Upgrading** notes on the
[releases page](https://github.com/retsu-AI/qq/releases).
Upgrade/restart server and clients together when the protocol changes.
`qq version` shows the store schema QQ migrates to on first open; migrations
are forward-only, so rollback needs the old binary and a pre-upgrade backup.

## Uninstall

Remove the binary/selection link (`rm ~/.local/bin/qq`, `brew uninstall qq`,
`nix profile remove`, or `cargo uninstall qq`). For script installs, inspect
and optionally remove `~/.local/bin/.qq-versions` too (or the corresponding
chosen install directory); this deletes retained rollback executables. Then optionally:

| Remove | Path (`qq config paths` prints yours) |
| --- | --- |
| configuration | the `global:` directory |
| sessions and trust state | the `data:` directory |
| credentials | `qq auth list`, then `qq auth logout <name>` for each |
