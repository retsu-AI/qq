## Unreleased

### Upgrading
- Contracts changed since v0.1.9: `PROTOCOL_VERSION` 40 → 42, `STORE_SCHEMA_VERSION` 64 → 65; `DESCRIPTOR_VERSION` stays 16 and `CAPABILITIES_VERSION` stays 1. Upgrade clients and servers together and run `qq daemon restart`. The store migrates forward on first open and v0.1.9 cannot open it afterwards; back up `sessions.sqlite3` (with any `-wal`/`-shm` files) first, as described for v0.1.9 below.
- Shell commands now run in the session's working directory (your checkout), as you, with QQ's full environment, your network and your real HOME. There is no private task copy, no publication step, no network isolation and no operating-system sandbox (Landlock, seccomp and namespaces on Linux, Seatbelt on macOS, the restricted token and AppContainer on Windows). Linux no longer needs unprivileged user namespaces, a root-owned `unshare` or Landlock. Each command still runs in its own process group (a job on Windows), and a timeout or cancellation kills it. For stronger isolation, run QQ in a container, a VM or a dedicated account.
- Stop every v0.1.9 QQ process before upgrading, including any `qq _command-owner` worker (`pkill -f '_command-owner'` on Unix): v0.1.10 never contacts them, so their commands would keep running unobserved. Unpublished Auto work from v0.1.9 stays under `<data>/qq/task-workspaces/` (`qq config paths` shows `<data>`); copy out anything you need, then delete the directory. `<data>/qq/command-owner-v3/` can be deleted too.
- A command no longer survives a daemon restart or crash: its process tree is killed when the QQ process that started it exits (SIGKILL included), and unfinished runs are reported as interrupted on restart.
- Ask asks you for each non-read call, `y` or `n`. Auto runs everything except the fixed stops and managed denies; Full also runs the fixed stops. Headless Ask denies at once. There is no approval reviewer and no stored approval: a removed setting below fails to load with a message naming its replacement.
- Removed configuration keys (delete them):
  - `policy.allow_tools`: Auto and Full run tools without grants; hide a tool from the model with `policy.exposed_tools`.
  - `policy.allow_shell_prefixes`: Auto runs commands without grants; restrict commands with managed `deny_shell_prefixes`.
  - `policy.allow_hosts`: Auto and Full fetch public hosts without grants; restrict hosts with managed `deny_hosts`.
  - `policy.shell_env`: commands inherit QQ's whole environment.
  - `policy.task_hosting`: run `git push` (and `gh`) from the shell in Auto or Full.
  - `reviewer_model`: Auto runs without a reviewer; Ask asks you.
  - `approval_delegate`, at the top level and in profiles: choose `approval_mode` `auto` or `full` to skip prompts, or `ask` to approve each call.
- Removed environment variable: `QQ_APPROVAL_DELEGATE` (setting it is an error); use `--approval` or `approval_mode`.
- Removed CLI flags and fields: `qq run --allow-tool`, `--allow-shell` and `--allow-host` (now an error; use `--approval auto` or `full`); the `approval_delegate`, `grant.tool.NAME` and `grant.shell.PREFIX` fields of `qq config explain`; the `policy grants` lines of `qq config show`; the hidden `_command-owner`, `_command-exec` and `_task-git` entry points.
- Removed from the TUI: `/delegate`, and the `a` (allow for the session) and `w` (write into `.qq/config.ron`) keys at an approval prompt.
- Removed tools: `task_commit`, `task_push` and `task_pr`; use `git` from the shell in Auto or Full. The `env` argument of `shell` and `exec` is gone; commands inherit the environment.
- Removed from the wire (protocol 41): the `approve_for_session` and `approve_for_workspace` decisions and their `grant` shapes (use `approve_once`); the `approved_for_session`, `approved_for_workspace`, `approved_by_reviewer` and `denied_by_reviewer` resolutions (recorded ones decode as `approved_once` and `denied`); `delegate` on `tool_approval_resolved`; `delegated` on `tool_approval_requested` and `pending_holds`; `escalated` on approval previews; `SessionSummary.approval_delegate`; the `set_approval_delegate` command and `POST /v1/sessions/approval-delegate`; and the `tool_approval_escalated`, `workspace_grant_promoted` and `approval_delegate_set` events (recorded ones decode as `retired`).
- Removed for contributors: `cargo xtask action-bias` and its runbook. The new `run-in-place` smoke scenario covers running in the checkout.

## 0.1.9 — 2026-10-26

### Upgrading
- Contracts changed since v0.1.8 (0ver: PATCH release, ADR-0051): `PROTOCOL_VERSION` 35 → 40, `DESCRIPTOR_VERSION` 15 → 16, `STORE_SCHEMA_VERSION` 58 → 64; `CAPABILITIES_VERSION` stays 1.
- Upgrade clients and servers together and restart every long-running `qq serve`: a client refuses a server on a different protocol. From this release on, `qq daemon restart` also replaces a daemon started by another version.
- The session store migrates forward on first open; v0.1.8 cannot open the migrated store. Before upgrading, run `qq config paths` and locate the actual `data` directory. Stop every QQ process (`qq serve`, the TUI, and any `qq run`) and copy `sessions.sqlite3` together with any adjacent `sessions.sqlite3-wal` and `sessions.sqlite3-shm` into a separate backup directory. If processes must remain running, use SQLite's consistent backup instead: replace both placeholders with absolute paths, verify the source file exists, then run `sqlite3 -readonly "/absolute/path/from/qq-config-paths/data/sessions.sqlite3" ".backup '/absolute/path/to/backup/sessions.sqlite3'"`. Never use a relative source path: it can select or create the wrong database. Rollback requires stopping all QQ processes, restoring the pre-upgrade backup at the original data-directory path without retaining migrated WAL/SHM files, and using the v0.1.8 binary. Keep the backup until the upgrade is verified.
- Approval modes are now `read_only`, `ask`, `auto` (the default) and `full`. Sessions stored with the retired `supervised` mode, which earlier releases gave write sub-agents, migrate to `auto`. Auto no longer prompts or consults a reviewer model: it runs edits in a private task copy of the workspace and shell commands in the native sandbox, and denies what falls outside them. Only `ask` asks a human. See the Permissions guide.
- Shell commands now always run in the operating system's sandbox, with no unsandboxed fallback. On Linux that needs a non-root user, unprivileged user namespaces and a root-owned `unshare`, and Auto also needs Landlock ABI 6 (Linux 6.12+); the Install guide lists every platform's requirements.
- The Jev integration is removed. A configuration that still sets `jev_review`, `jev_routing` or `jev_approval` no longer loads; delete those keys.
- The TUI no longer prompts to trust a project. Untrusted sensitive project settings are ignored at startup; review them and run `qq trust` to enable them, and `qq config sources` lists what is waiting.

## 0.1.5 — 2026-09-29

### Upgrading
- Contracts changed since v0.1.4 (0ver: shipped as a PATCH release, ADR-0051): `PROTOCOL_VERSION` 27 → 30, `DESCRIPTOR_VERSION` 9 → 12, `STORE_SCHEMA_VERSION` 35 → 39; `CAPABILITIES_VERSION` stays 1.
- Restart any long-running `qq serve` and upgrade its clients together: a client refuses a server on a different protocol.
- The session store migrates forward on first open, and v0.1.4 cannot open it afterwards. If you might roll back, stop every QQ process first (`qq serve`, the TUI, any `qq run`), then copy `sessions.sqlite3` together with any `sessions.sqlite3-wal` and `sessions.sqlite3-shm` beside it: the store runs in WAL mode, so recent history may live in the `-wal` file until the last process closes. Or, with the processes still running, take a consistent copy with `sqlite3 sessions.sqlite3 ".backup backup.sqlite3"`.
- `reasoning_effort` values a model does not list in its known accepted set now fail at plan time with the accepted values named: for example `minimal` on GPT-6 Astra, `xhigh` on Claude 4.6, `none`/`minimal` on Anthropic. Pick an accepted value, or `default` to let the provider choose.
- `jev_approval` now follows the run's profile and applies to the next run without a restart; a profile's `jev_approval: false` turns Jev approval off for that profile.
